# 性能优化与生产化

> 这一章把程序从“能跑”推到“能上线”：批处理、prefetch、cache、NUMA、退出路径、安全权限、排障和生产检查。

## 23. 性能优化路线

### 23.1 先保证正确

优化前先满足：

- 不泄漏 mbuf。
- `tx_burst` 未发送部分有处理。
- 多段包策略明确。
- 包头长度检查完整。
- lcore 和 queue ownership 明确。
- 退出路径能 stop/close port。
- 统计能解释丢包原因。

### 23.2 批处理

DPDK 的性能来自批处理。常用 `BURST_SIZE`：

```c
#define BURST_SIZE 32
```

经验：

- 16、32、64 都值得压测。
- 大 burst 通常吞吐更好，但延迟可能增加。
- 小 burst 延迟更低，但函数调用和 PCI 访问成本更高。
- 不同网卡和包长会有不同最优值。

### 23.3 prefetch

处理数组中的包时可以预取后面的包：

```c
for (uint16_t i = 0; i < nb_rx; i++) {
    if (i + 4 < nb_rx) {
        rte_prefetch0(rte_pktmbuf_mtod(bufs[i + 4], void *));
    }

    /* process bufs[i] */
}
```

prefetch 不是越多越好。过早预取会挤占 cache，过晚预取来不及。要用性能计数器和压测判断。

### 23.4 cache line 和 false sharing

数据面结构体要关注 cache line：

- 每个 lcore 的计数器放独立 cache line。
- 热字段放一起，冷字段拆出去。
- 只读配置和频繁写统计分开。
- 避免多个核心频繁写同一个 cache line。

示例：

```c
struct lcore_stats {
    uint64_t rx;
    uint64_t tx;
    uint64_t drop;
} __rte_cache_aligned;
```

### 23.5 分支和慢路径

数据面循环应该让常见路径短而直：

- 常见包类型走 fast path。
- 异常包、控制包、未知协议走 slow path。
- 使用 `likely()`、`unlikely()` 标注明显分支。
- 不在 fast path 打日志。
- 不在 fast path 做阻塞 IO。

### 23.6 避免每包锁

每包锁通常是吞吐杀手。替代方法：

- 每 lcore 独立状态。
- RCU 风格读多写少配置。
- 批量更新。
- ring 消息传递。
- 控制面构建新表，数据面原子切换指针。

### 23.7 NUMA 优化

NUMA 问题经常表现为“代码看起来没问题，但性能只有别人一半”。

检查：

```bash
numactl --hardware
lscpu -e
cat /sys/bus/pci/devices/0000:03:00.0/numa_node
```

优化：

- port 在 node0，worker 也放 node0。
- mempool 在 node0 创建。
- hugepage 在 node0 预留。
- 避免 worker 在 node1 频繁访问 node0 NIC。

### 23.8 系统级调优

常见调优项：

```bash
# CPU governor
cpupower frequency-set -g performance

# 查看中断
cat /proc/interrupts

# 查看调度迁移
pidstat -w -p <pid> 1

# perf 采样
perf top -p <pid>
perf record -F 99 -p <pid> -- sleep 30
perf report
```

还要关注：

- BIOS C-state。
- Turbo 策略。
- SMT/超线程是否开启。
- IRQ affinity。
- NIC firmware。
- PCIe 插槽带宽。
- 交换机流控、pause frame。
- 网线和光模块错误。

## 24. 可靠性与退出路径

### 24.1 信号处理

数据面程序应支持优雅退出：

- SIGINT/SIGTERM 设置 `force_quit`。
- worker 看到标志后退出循环。
- 停止端口。
- 释放或 drain ring 中的 mbuf。
- close ethdev。
- `rte_eal_cleanup()`。

不要在 signal handler 里调用复杂 DPDK API。handler 只设置标志。

### 24.2 错误路径释放

初始化过程要设计 rollback：

- 端口启动失败，关闭已启动端口。
- queue setup 失败，停止该端口。
- mempool 创建失败，直接退出。
- ring/hash/LPM 创建失败，释放已创建资源。

C 代码可以用 `goto cleanup` 管理复杂错误路径，别为了“看起来优雅”复制粘贴一堆释放逻辑。

### 24.3 链路和设备异常

生产系统要考虑：

- 链路 down/up。
- 网卡 reset。
- 驱动错误。
- hotplug。
- 队列异常。
- 对端流量突增。

最少也要周期性检查链路状态和错误统计，并把异常暴露给监控系统。

## 25. 安全与权限

DPDK 程序经常需要访问 hugepage、VFIO、PCI 设备和锁定内存，因此很多示例直接用 root。但生产环境应尽量收敛权限。

建议：

- 优先使用 VFIO 和 IOMMU。
- 通过组权限管理 `/dev/vfio/*`。
- 限制 hugepage 目录权限。
- 给进程设置合理的 `memlock` limit。
- 避免 no-IOMMU 模式。
- 不把管理网口绑定到 DPDK。
- 控制 telemetry 和管理接口访问权限。
- 对控制面配置更新做鉴权和审计。

示例 limits：

```conf
dpdkuser soft memlock unlimited
dpdkuser hard memlock unlimited
```

## 26. 常见问题排查

| 现象 | 可能原因 | 排查命令/处理 |
| --- | --- | --- |
| `no available Ethernet ports` | 网卡未绑定、EAL 没允许设备、驱动不支持 | `dpdk-devbind.py --status`，检查 `-a` 参数 |
| EAL 初始化失败 | hugepage 不足、权限不足、参数错误 | `grep Huge /proc/meminfo`，检查 `/mnt/huge` |
| VFIO 报 IOMMU 问题 | BIOS 或内核参数未启用 IOMMU | 检查 grub，`dmesg | grep -i iommu` |
| 远程机器断连 | 管理网口被解绑 | 使用带外管理恢复，生产前标记管理口 |
| 收不到包 | 链路 down、对端没发、RSS/queue 错、promisc 未开 | `testpmd`、`show port stats all`、交换机镜像 |
| `rx_nombuf` 增长 | mempool 太小、mbuf 泄漏、TX 不回收 | 增大 pool，检查 free 路径 |
| TX 只发一部分 | TX queue 满或链路问题 | 处理 `nb_tx < nb_rx`，看 xstats |
| 吞吐低 | NUMA 远端、CPU 频率低、burst 太小、offload 配错 | `lscpu -e`、`perf top`、调 burst |
| 延迟抖动 | 控制面干扰、日志过多、跨核 ring 堆积 | 隔离核心，减少慢路径 |
| 程序退出后 hugepage 仍被占 | 进程崩溃或 backing file 残留 | 确认无进程占用，清理 hugetlbfs 文件 |
| 多进程 attach 失败 | `file-prefix` 不一致或 primary 未启动 | 统一参数，确认启动顺序 |
| checksum 错 | offload 配置和 mbuf 标志不匹配 | 关闭 offload 验证，再逐项打开 |

## 27. 工程目录建议

一个中等规模 DPDK 项目可以这样组织：

```text
dpdk-app/
  meson.build
  include/
    app_config.h
    port.h
    worker.h
    stats.h
    flow_table.h
  src/
    main.c
    eal_args.c
    port.c
    worker.c
    stats.c
    flow_table.c
    control_plane.c
  conf/
    app.toml
  scripts/
    setup_hugepages.sh
    bind_nic.sh
    run_testpmd.sh
  tests/
    unit/
    pcap/
```

模块职责：

| 模块 | 职责 |
| --- | --- |
| `main.c` | 启动顺序、信号、生命周期 |
| `port.c` | ethdev 配置、queue setup、链路状态 |
| `worker.c` | 数据面循环 |
| `flow_table.c` | hash/LPM/ACL/rte_flow 封装 |
| `stats.c` | per-lcore 统计、汇总、输出 |
| `control_plane.c` | 配置加载、更新、管理接口 |
| `scripts/` | 环境准备、绑定网卡、压测命令 |

## 28. 开发阶段路线图

### 阶段 1：环境闭环

目标：

- DPDK 能编译。
- hugepage 正常。
- 网卡能绑定到 VFIO。
- testpmd 能收发包。

验收：

```bash
sudo dpdk-devbind.py --status
grep Huge /proc/meminfo
sudo ./build/app/dpdk-testpmd -l 1-3 -n 4 -a <pci> -- --auto-start
```

### 阶段 2：最小程序

目标：

- 自己的程序能启动 EAL。
- 能初始化端口。
- 能收包并释放。
- 能输出统计。

验收：

- 收包计数和对端发包一致。
- Ctrl+C 可干净退出。
- `rx_nombuf` 不增长。

### 阶段 3：单核转发

目标：

- port0 到 port1 转发。
- 处理 `tx_burst` 部分发送。
- 支持基础 MAC 改写。

验收：

- testpmd 或流量发生器看到正确转发。
- 不泄漏 mbuf。
- 小包吞吐达到预期基线。

### 阶段 4：多队列多核

目标：

- 配置 RSS。
- 每个 worker 处理独立 queue。
- per-lcore 统计。

验收：

- 多流能均匀分布到 queue。
- 单流不会乱序。
- CPU 和 NIC NUMA 匹配。

### 阶段 5：业务逻辑

目标：

- 引入 hash/LPM/ACL。
- 支持配置加载。
- 支持运行期统计查询。
- 支持明确的 drop reason。

验收：

- 功能测试覆盖关键规则。
- 性能压测覆盖最大规则量。
- 配置更新不造成明显抖动。

### 阶段 6：生产化

目标：

- systemd 服务。
- 权限收敛。
- 监控和日志。
- 异常处理。
- 回滚脚本。
- 网卡恢复脚本。

验收：

- 重启后自动准备 hugepage 和绑定。
- 服务异常退出可恢复。
- 管理网口不会被误绑定。
- 监控能解释吞吐、丢包和错误。

## 29. 生产检查清单

上线前逐项确认：

- [ ] DPDK 版本、NIC firmware、内核版本记录清楚。
- [ ] 网卡型号和 PMD 能力验证过。
- [ ] 管理网口不会被绑定到 DPDK。
- [ ] hugepage 按 NUMA 预留并持久化。
- [ ] VFIO/IOMMU 启用，未使用 no-IOMMU 生产运行。
- [ ] lcore 规划固定，数据面核心隔离。
- [ ] RX/TX queue 和 lcore ownership 明确。
- [ ] mempool 大小经过突发和拥塞测试。
- [ ] `tx_burst` 部分发送有处理。
- [ ] 所有 drop reason 有统计。
- [ ] xstats 和链路状态进入监控。
- [ ] Ctrl+C、SIGTERM、服务停止能干净释放资源。
- [ ] 重启后端口能重新绑定或恢复。
- [ ] 配置更新路径有鉴权和回滚。
- [ ] 压测覆盖最小包、混合包长、长流、短流和异常包。
